    Request & worker flows

    This page traces a design from ingestion to public visibility. Endpoints are mounted under /api (see app.main); the route modules themselves are in app.api.routes.

    Conversion status state machine

    Every Patent carries a ConversionStatus. The two ingestion paths share the tail of the pipeline.

    stateDiagram-v2
    [*] --> UPLOADED: POST /patents/upload
    [*] --> QUEUED: POST /patents/generate

    UPLOADED --> QUEUED: POST /{id}/convert
    QUEUED --> GENERATING: generator picks up (image-gen only)
    GENERATING --> QUEUED: GLB wrapped, handed to convert queue
    QUEUED --> CONVERTING: worker picks up
    CONVERTING --> CONVERTED: GLB written, thumbnail attempted
    CONVERTING --> FAILED: converter error
    GENERATING --> FAILED: Hunyuan error
    FAILED --> QUEUED: POST /{id}/convert (retry)
    • UPLOADED — ZIP stored, conversion is user-triggered.
    • QUEUED — a Celery task is enqueued and waiting for a worker.
    • GENERATING — the generator is running Hunyuan3D (image-gen only).
    • CONVERTING — an ephemeral converter container is running.
    • CONVERTED — GLB ready; the thumbnail step flips this flag (best-effort).
    • FAILED — the last attempt failed; conversion_error holds the message.

    See the enum in app.models.patent.

    ZIP upload → conversion

    sequenceDiagram
    participant U as Client
    participant API as FastAPI
    participant DB as Postgres
    participant Q as Redis
    participant W as Celery worker
    participant C as Converter container

    U->>API: POST /patents/upload (zip + form)
    API->>API: validate_zip_upload (bomb/MIME/size/structure)
    API->>DB: INSERT patent (UPLOADED)
    API-->>U: 202 {patent_id, UPLOADED}

    U->>API: POST /patents/{id}/convert
    API->>DB: status = QUEUED
    API->>Q: convert_patent_task.delay(id)
    API-->>U: 202 {QUEUED}

    W->>Q: pick up task
    W->>DB: status = CONVERTING
    W->>C: docker create (network none, cap-drop all)
    W->>C: docker cp zip in
    W->>C: docker start (xvfb-run main.py)
    C-->>W: output.glb (+ optional *_errors.json)
    W->>W: docker cp glb out → media volume
    W->>DB: glb_file_path set, warnings saved
    W->>Q: generate_thumbnail_task.delay(id)
    W->>DB: status = CONVERTED (set by thumbnail task)

    The upload is validated up front by validate_zip_upload: a zip-bomb scan (overlapping-records detector), symlink and path-traversal rejection, entry-count and uncompressed-size and compression-ratio caps, a single-model-file rule (.obj must ship exactly one .mtl), and a libmagic MIME whitelist on the model file itself.

    The conversion task itself lives in convert_patent_task. Soft warnings emitted by the converter (import_errors.json / export_errors.json) are pulled out, tagged with a phase, and stored on Patent.conversion_warnings so the UI can show a ⚠ badge without failing an otherwise-successful conversion.

    Upload, then convert

    # 1. Register the design (multipart): model ZIP + classification + scale
curl -X POST http://localhost:8000/api/patents/upload \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@chair.zip" \
  -F "design_name=Ergonomic Chair" \
  -F "locarno_main_class=SINIF_6" \
  -F "locarno_subclass=SINIF_6_01" \
  -F "scale=MM"
# -> 202 {"patent_id": 42, "status": "UPLOADED", ...}

# 2. Trigger conversion
curl -X POST http://localhost:8000/api/patents/42/convert \
  -H "Authorization: Bearer $TOKEN"
# -> 202 {"patent_id": 42, "status": "QUEUED"}

# 3. Poll until CONVERTED (or FAILED)
curl http://localhost:8000/api/patents/42/status \
  -H "Authorization: Bearer $TOKEN"

    Image-to-3D generation

    The generate path produces a GLB from reference photos, then rejoins the conversion pipeline above.

    sequenceDiagram
    participant U as Client
    participant API as FastAPI
    participant G as Celery generator
    participant HY as Hunyuan3D (host)
    participant W as Celery worker

    U->>API: POST /patents/generate (1-4 images)
    API->>API: validate_and_reencode each view → PNG
    API->>API: INSERT patent (IMAGE, QUEUED); store views
    API->>G: generate_from_image_task.delay(id, overrides)
    API-->>U: 202 {QUEUED}

    G->>API: status = GENERATING
    G->>HY: POST /generate (multi-view base64)
    HY-->>G: GLB bytes
    G->>G: wrap GLB in a ZIP on the media volume
    G->>W: convert_patent_task.delay(id)  (status QUEUED)
    Note over W: identical convert + thumbnail path as an upload

    Images are validated and re-encoded by validate_and_reencode (size and dimension caps, re-encode to PNG RGBA to strip EXIF/ICC). UI presets map to pipeline params: quality → num_inference_steps, detail → octree_resolution (see the QUALITY_PRESETS / DETAIL_PRESETS tables in app.api.routes.patents). The generation task is generate_from_image_task.

    Expert review lifecycle

    Moderation state is derived from design_reviews rows, never stored on the patent. A design is public only once it has an APPROVED review.

    stateDiagram-v2
    [*] --> DRAFT: created / re-opened
    DRAFT --> UNDER_REVIEW: owner POST /{id}/submit
    REJECTED --> UNDER_REVIEW: owner edits & resubmits
    UNDER_REVIEW --> APPROVED: expert approve (public, terminal)
    UNDER_REVIEW --> REJECTED: expert reject (+reason)
    APPROVED --> [*]
    State Who sees the design Owner can edit?
    DRAFT Owner (private preview), admins, experts Yes
    UNDER_REVIEW Admins, experts. Obscured even from the owner. No (locked)
    APPROVED Everyone (public catalog + anonymous QR scans) No (locked)
    REJECTED Owner (with the reason), admins, experts Yes — edit & resubmit

    The state function and helpers are in app.models.review; the owner-facing transitions (submit, reupload, metadata PATCH) are in app.api.routes.patents and the expert decisions in app.api.routes.expert.

    Expert approves a submission

    # The shared queue of submissions awaiting evaluation
curl http://localhost:8000/api/expert/submissions \
  -H "Authorization: Bearer $EXPERT_TOKEN"

# Approve (design becomes public) ...
curl -X POST http://localhost:8000/api/expert/submissions/42/approve \
  -H "Authorization: Bearer $EXPERT_TOKEN"

# ... or reject with a reason (re-opens for the owner)
curl -X POST http://localhost:8000/api/expert/submissions/42/reject \
  -H "Authorization: Bearer $EXPERT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "Mesh has inverted normals on the seat."}'

    Media access and the QR capability token

    Models, thumbnails, and source images are served by app.api.routes.patents. Access follows the review state via _can_view_media: APPROVED designs are public; otherwise only the owner (for DRAFT/REJECTED), experts, admins, or a holder of a valid media token may fetch them.

    The media token is a short-lived, single-patent capability token minted by create_media_token and verified by verify_media_token. It is encoded into QR links so an unauthenticated AR scanner can open a not-yet-public design's model:

    graph LR
    O[Owner opens detail page] -->|GET /patents/id| API
    API -->|mints model_token if CONVERTED| O
    O -->|builds QR with ?token=...| QR[QR code]
    QR -->|scan| AR[AR client]
    AR -->|GET /patents/id/model?token=...| API
    API -->|verify_media_token| GLB[(GLB stream)]

    The token has a distinct scope and carries no sub, so a leaked media token cannot be used as a login and an access token cannot be used as a media token.
