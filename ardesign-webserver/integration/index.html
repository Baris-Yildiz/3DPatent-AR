    Plugging into the 3DPatent-AR site

    This doc set is a self-contained MkDocs project (fastapi_app/mkdocs.yml + fastapi_app/docs/) that mirrors the structure of the published 3DPatent-AR documentation: a Home page, a component section (Overview + Architecture), an mkdocstrings API Reference, and Deployment + Maintenance pages, all on Material for MkDocs.

    There are two ways to publish it alongside the existing site. The converter docs and the Unity AR docs are already two independent doc sets stitched together at the top level, so the sub-site approach below matches the existing pattern.

    Option A — separate sub-site (recommended)

    This is how unity-ar-docs/ is integrated today: a standalone build whose output is copied into the published site and linked from the home page.

    1. Build this project into static HTML: 
      cd fastapi_app
pip install -r docs-requirements.txt
mkdocs build            # outputs ./site
    2. Copy the output into the 3DPatent-AR site source (the converter/docs/ tree on the main-fbx branch) under a new folder, e.g. converter/docs/web-platform/, so it deploys as …/3DPatent-AR/web-platform/.
    3. Add a card to the site's home page (converter/docs/index.md) next to the existing Converter and Unity AR cards: 
      -   **Web Platform**

    FastAPI + Celery backend: ingestion, conversion, review workflow, and model serving.

    [View Docs](web-platform/index.html){ .md-button .md-button--primary }
    4. Re-run the site's own mkdocs build / mkdocs gh-deploy. The sub-site is shipped as static assets, so the main build needs none of the FastAPI dependencies.

    Option B — merge into the existing MkDocs project

    Fold these pages into the converter's mkdocs.yml as one unified site.

    1. Copy fastapi_app/docs/* into the site's docs directory under a web-platform/ subfolder (rename index.md to avoid clashing with the site root).
    2. Add the nav block from fastapi_app/mkdocs.yml (everything under Web Platform, API Reference, Deployment, Maintenance) into the site's nav:, prefixing each path with web-platform/.
    3. Make the FastAPI source importable to mkdocstrings. Either vendor the app/ package next to the docs and add it to paths, or point at it: 
      plugins:
  - mkdocstrings:
      handlers:
        python:
          paths: ["path/to/fastapi_app"]
      mkdocstrings reads the source statically (Griffe), so the app's runtime dependencies (FastAPI, SQLAlchemy, Celery, …) do not need to be installed — only the .py files must be reachable on paths.

    Why Option A is simpler here

    The converter docs live in the baris-yildiz/3DPatent-AR repo while the FastAPI source lives in this repo. Option A ships pre-rendered HTML, so the two repos stay decoupled — the site build never needs this repo's source. Option B gives a single search index and unified theme but couples the site build to this repo's app/ package.

    Conventions this project follows

    So future pages stay consistent with the rest of the site:

    • Material for MkDocs with navigation.tabs + navigation.sections.
    • mkdocstrings (Google-style docstrings, show_source, separate_signature, docstring_section_style: table) for every API Reference page — one ::: directive per module.
    • Mermaid diagrams via pymdownx.superfences for data flow, state machines, and the data model.
    • Admonitions (!!! note, !!! warning, !!! danger, !!! example) and tables for structured detail.
    • Each narrative page ends with a Next steps list of cross-links.
