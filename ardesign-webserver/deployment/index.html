    Deployment

    The platform ships as a Docker Compose stack. There are two compose files, kept isolated by Compose project name so dev and prod have independent databases and media volumes:

    Environment Compose file Project name
    Development docker-compose.yml arpatent
    Production docker-compose.prod.yml arpatent-prod

    The README is the canonical runbook

    fastapi_app/README.md holds the full, step-by-step operational guide (first-time setup, ngrok exposure, versioned deploys, rollbacks, TLS). This page is the architectural summary. Every command assumes you are inside fastapi_app/.

    Services

    Both compose files describe the same logical services (prod adds nginx, a frontend builder, and certbot):

    Service Image Role
    db postgres:15 Application database
    redis redis:7-alpine Celery broker + result backend
    api built from Dockerfile FastAPI (uvicorn in dev, gunicorn + 4 uvicorn workers in prod)
    worker same image as api Celery worker, default queue (conversion + thumbnail)
    generator same image as api Celery worker, generate queue (Hunyuan3D)
    socket-proxy tecnativa/docker-socket-proxy Mediates the worker's Docker API calls
    nginx (prod) nginx:alpine TLS-terminated reverse proxy + static SPA
    frontend-builder (prod) built from frontend/Dockerfile One-shot React build into a shared volume
    certbot (prod) certbot/certbot Dormant unless serving a real domain

    The api, worker, and generator share one image and the media_data volume. The worker additionally joins the internal proxy-net to reach the socket proxy; the generator gets a host.docker.internal host-gateway alias to reach the host-native Hunyuan3D server.

    The converter image is external

    The worker spawns youndria/arpatent containers as siblings; that image is not built from this repo. Pull it on the host first: 

    docker pull youndria/arpatent:1.5
    The exact tag is pinned in CONVERTER_IMAGE in app.worker.celery_app — bump it in one place.

    The application image

    Dockerfile builds a single python:3.11-slim image used by the api and both workers. It installs the Docker CLI (a no-op in the api container, used by the worker for DooD) and libmagic1 (for upload MIME sniffing), then runs as an unprivileged app user (UID 1000).

    docker build -t arpatent-api:v0.1.0 .   # tag must match APP_VERSION in .env

    Development quickstart

    docker-compose.yml bind-mounts the source for hot reload and hardcodes local credentials.

    cd fastapi_app
docker compose up --build           # db, redis, api, worker, generator, socket-proxy
docker compose exec api alembic upgrade head
    • API: http://localhost:8000 — interactive docs at /docs
    • Run the React frontend separately with Vite (cd frontend && npm install && npm run dev).

    Production overview

    docker-compose.prod.yml pins images by APP_VERSION, runs gunicorn with 4 workers behind nginx, sets per-service mem_limit / pids_limit, and caps container logs. The high-level sequence (see the README for the detail):

    cp .env.example .env                 # set POSTGRES_PASSWORD, JWT_SECRET_KEY, CORS_ORIGINS, APP_VERSION
docker pull youndria/arpatent:1.5
docker build -t arpatent-api:v0.1.0 .
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml run --rm api alembic upgrade head
ngrok http 80                        # public TLS edge

    Never down -v in production

    The -v flag deletes the named volumes — the Postgres database and every uploaded model. It is a dev-only reset button.

    Configuration

    All runtime config is environment-driven through app.core.config.Settings, loaded from .env. Required secrets have no default and must be supplied: POSTGRES_PASSWORD and JWT_SECRET_KEY. See .env.example for the full set.

    Migrations

    Alembic migrations are a deliberate step, never run automatically on container start, so a failed migration aborts the release before traffic shifts.

    # dev
docker compose exec api alembic upgrade head
# prod (disposable one-shot container)
docker compose -f docker-compose.prod.yml run --rm api alembic upgrade head

    Autogenerate misses column renames, check constraints, Postgres enum value additions (write op.execute("ALTER TYPE ... ADD VALUE ...") by hand), and data backfills — review every generated revision. Full rules in the README.

    Bootstrapping the first admin

    There is no HTTP route to self-promote. The first admin is created out-of-band with a management command that ships inside the image (app.scripts.set_admin):

    docker compose -f docker-compose.prod.yml exec api python -m app.scripts.set_admin <username>

    The user must already exist (register first) and must re-login for the new role to take effect. After that, role changes go through PATCH /api/admin/users/{id}. The command refuses to demote or remove the last active admin.
