    Architecture

    The platform runs as a small set of cooperating containers. The API process serves HTTP and never blocks on heavy work; everything slow (conversion, thumbnailing, image generation) is pushed to Celery workers over Redis. State lives in PostgreSQL, and binary artifacts live on a shared media volume.

    Service topology

    graph TD
    subgraph client[Clients]
        B[Browser / React SPA]
        AR[Unity AR client]
    end

    B -->|HTTPS| API[FastAPI api<br/>uvicorn]
    AR -->|HTTPS + media token| API

    API -->|async asyncpg| PG[(PostgreSQL)]
    API -->|enqueue| R[(Redis broker)]
    API -->|read/write artifacts| MV[[media volume]]

    R --> W[Celery worker<br/>queue: celery]
    R --> G[Celery generator<br/>queue: generate]

    W -->|sync psycopg2| PG
    G -->|sync psycopg2| PG
    W --> MV
    G --> MV

    W -->|docker API| SP[docker-socket-proxy]
    SP -->|spawn ephemeral| CONV[youndria/arpatent<br/>converter + thumbnailer]
    G -->|HTTP| HY[host-native<br/>Hunyuan3D API]

    W -. docker cp in/out .-> CONV
    • api — FastAPI under Uvicorn (dev) / Gunicorn (prod). Async end to end: asyncpg to Postgres, non-blocking request handling. Enqueues Celery tasks but never runs them.
    • worker — Celery worker on the default celery queue (--concurrency=1). Runs convert_patent_task and generate_thumbnail_task, which drive the ephemeral converter containers via Docker-out-of-Docker (DooD).
    • generator — a second Celery worker bound to the generate queue (--concurrency=1). Isolated because Hunyuan3D needs a GPU and serializes to a single in-flight request.
    • socket-proxy — tecnativa/docker-socket-proxy, the only thing with access to the Docker socket. The worker talks to it (DOCKER_HOST=tcp://socket-proxy:2375) so a compromised worker can't reach the full host daemon directly.
    • db / redis — PostgreSQL 15 and Redis 7.

    The converter container is not mounted

    The ephemeral youndria/arpatent containers run with --network none, --cap-drop ALL, --security-opt no-new-privileges, and no volume mounts. The worker streams the input ZIP in and the GLB / warning JSONs out with docker cp, so the job is fully isolated from the host filesystem and network. See app.worker.tasks.

    Two database sessions, by design

    FastAPI is async and Celery is sync, so there are two SQLAlchemy engines against the same database:

    graph LR
    subgraph asyncside[FastAPI request path]
        AR2[route] --> AS[get_db<br/>AsyncSession] --> AE[asyncpg engine]
    end
    subgraph syncside[Celery task path]
        CT[task] --> SS[SyncSessionLocal<br/>Session] --> SE[psycopg2 engine]
    end
    AE --> DB[(PostgreSQL)]
    SE --> DB
    • Routes depend on get_db which yields an AsyncSession (app.db.session).
    • Tasks open a SyncSessionLocal (app.db.sync_session) directly — they are plain functions running in a worker process, not in the event loop.

    Both URLs are derived from one settings object — see Settings.database_url / Settings.sync_database_url.

    Code layers

    The app/ package is organised by responsibility. Dependencies point downward; nothing in a lower layer imports an upper one.

    graph TD
    main[app.main<br/>FastAPI app + CORS + routers] --> routes
    routes[app.api.routes<br/>auth · patents · locarno · admin · expert] --> deps[app.api.deps<br/>auth gates]
    routes --> schemas[app.schemas<br/>Pydantic DTOs]
    routes --> core[app.core<br/>security · upload validation · config]
    routes --> data[app.data.locarno<br/>read helpers]
    routes --> models
    routes -->|enqueue| worker[app.worker.tasks<br/>Celery tasks]
    worker --> models
    worker --> core
    deps --> models[app.models<br/>SQLAlchemy ORM]
    data --> models
    models --> base[app.db.base / session / sync_session]
    Layer Package Responsibility
    Entrypoint app.main Builds the FastAPI app, adds CORS, mounts routers under /api, exposes /health.
    Routes app.api.routes HTTP endpoints, grouped by feature. Admin and expert routers gate every sub-route at the package level.
    Dependencies app.api.deps get_current_user and the role gates (*_admin_user, *_expert_user, get_optional_user).
    Schemas app.schemas Pydantic request/response models. Response models never leak password hashes or hidden review state.
    Core app.core Settings, JWT + password + media-token helpers, ZIP and image upload validation.
    Models app.models SQLAlchemy ORM entities and the derived review-state logic.
    Data app.data.locarno Thin read helpers over the Locarno lookup tables.
    Workers app.worker Celery app config and the conversion / thumbnail / generation tasks.

    class LocarnoMainClassRow {

    User "1" --> "0..*" Patent : owns
    Patent "1" --> "0..*" DesignReview : review cycles
    User "1" --> "0..*" DesignReview : reviewed_by
    LocarnoMainClassRow "1" --> "0..*" LocarnoSubclassRow : subclasses

    Two modelling decisions are worth calling out:

    • Review state is derived, not stored. A Patent has no status column for moderation. Each submit/decision cycle is a DesignReview row, and the effective state (DRAFT / UNDER_REVIEW / APPROVED / REJECTED) is computed from those rows by effective_review_state. This keeps the full audit trail (every reject + resubmit) and keeps lifecycle fields off the core entity.
    • Locarno classification is referenced by string, not foreign key. A Patent stores the Locarno value strings directly. The lookup tables hold the canonical hierarchy (5000+ subclasses — too many for a native enum), and the admin Locarno routes enforce referential integrity in application code before any delete. See app.api.routes.admin Locarno management.
